# ADR-0004. 방문 · 방문자 · 신청 · 전환율의 정의와 측정 방법

- 상태: 채택
- 관련 요구사항: §2 "캠페인별 방문, 방문자, 신청, 전환율", "채널별 성과"
- 구현: `apps/admin/src/lib/stats.ts`, `apps/forms/src/app/f/[slug]/route.ts`

## 맥락

과제는 **방문**과 **방문자**를 구분해서 요구한다. 방문자(고유한 사람)를 어떻게 식별할지, 전환율의 분모를 무엇으로 할지는 문서에 없으므로 합리적 가정을 세워 기록한다(§7).

## 결정

| 지표 | 정의 | 측정 |
|---|---|---|
| 방문 (visits) | 공개 폼 페이지(`/f/{slug}`) 로드 1회 | 서버가 응답 전에 `visits` 에 1행 insert |
| 방문자 (visitors) | 고유 `visitor_id` 수 | forms origin 의 1st-party 쿠키 `lm_vid`(UUID v4, 1년, HttpOnly, SameSite=Lax). 없으면 발급 |
| 신청 (leads) | 저장된 리드 수 | `leads` 행 수 |
| 전환율 | **신청 ÷ 방문자** (방문자 0 이면 0) | 소수로 반환(0.5), UI 에서 % 표기 |

- 채널 귀속: URL 의 `c` 파라미터(배포 링크 코드)를 `distribution_links` 에서 찾아 `link_id` 로 기록. 코드가 없거나 모르는 값이면 `link_id = NULL` → 채널별 성과에서 **DIRECT(직접 유입)** 로 표시.
- 제출 시에도 `code` 와 `lm_vid` 를 함께 저장해, 방문과 신청이 같은 링크·같은 방문자로 연결된다.
- **미리보기(`/p/{slug}`)는 방문으로 세지 않는다.** 운영자가 콘솔에서 폼을 확인하는 행위가 성과를 오염시키면 안 된다.
- **마감된 폼(410)과 없는 폼(404)** 은 방문을 기록하지 않는다.
- 캠페인 상태가 공개 여부를 결정한다: `PAUSED`/`ARCHIVED` → 410. 폼 자체의 `is_active=false` 도 410.

## 대안과 기각 이유

- **전환율 = 신청 ÷ 방문** — 같은 사람이 새로고침만 해도 전환율이 떨어져 채널 비교가 왜곡된다. 마케팅에서 통용되는 "방문자 대비 전환" 이 채널 성과 비교에 더 적합하다.
- **방문자 식별을 IP + User-Agent 해시로** — 쿠키 없이 동작하는 장점이 있지만, 같은 회사/카페 와이파이의 여러 사람이 한 명으로 뭉치고 모바일 IP 는 자주 바뀐다. 1st-party 쿠키가 정확도와 구현 단순성 모두 낫다. 쿠키 거부/삭제 시 과대 집계되는 한계는 받아들인다.
- **클라이언트 비콘(JS)으로 방문 기록** — 서버 측 기록이 더 단순하고 봇/스크립트 차단에도 영향받지 않는다. 대신 크롤러 방문이 섞일 수 있는데, 필요 시 UA 기반 봇 필터를 서버에서 추가할 수 있도록 `user_agent` 를 저장해 두었다.

## 결과

- 지표 계산 예: 방문자 A 가 인스타 링크로 3번 열고 1번 신청, B 가 인스타로 1번 열고 이탈, C 가 유튜브로 1번 열고 신청, D 가 직접 1번 → 캠페인: 방문 6 / 방문자 4 / 신청 2 / 전환율 50%. 인스타: 4/2/1/50%, 유튜브: 1/1/1/100%, DIRECT: 1/1/0/0%. (`apps/admin/tests/campaign-flow.test.ts` 로 고정)
- 같은 방문자의 중복 신청은 막지 않는다(한 사람이 지인 여러 명을 대신 신청하는 경우 등). 필요하면 `(form_id, visitor_id)` 인덱스가 이미 있어 중복 판별을 쉽게 붙일 수 있다.
